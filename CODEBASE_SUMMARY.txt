CODEBASE SUMMARY FOR CLAUDE OR ANY OTHER CODING AGENT

Purpose
This repository is an in-progress admin platform for an IAC (Internet Access Centre / facility management) product. The codebase mixes:
- a real Express + Mongo backend,
- a real Next.js dashboard frontend,
- several static HTML design/prototype folders,
- and a number of feature areas that are only partially wired end to end.

The safest mental model is: "production-shaped backend plus a partially integrated dashboard plus design references."


1. REPO SHAPE

Top level:
- backend/
- frontend/

backend/:
- Real Node/Express API.
- Uses MongoDB via Mongoose.
- Authentication is JWT-based with an access token plus refresh-token cookie.
- Most business logic lives directly inside route files.
- There are placeholder directories such as backend/src/controllers and backend/src/services, but they are currently empty.

frontend/iacmanager/:
- Real Next.js App Router project.
- This is the actual dashboard/front-end app.
- Uses React 19, Next 16, TypeScript, Tailwind v4, CSS modules, and a lot of inline styling.
- Calls the backend directly through a small fetch wrapper in src/lib/api.ts.

frontend/<other folders>/:
- Folders like user_management, device_control_board, internet_access_qr_tokens, room_management, report_builder, cctv_monitoring, dashboard_overview, software_deployment.
- These mostly contain code.html and screen.png files.
- Treat them as static design/prototype artifacts, not the main running app.

frontend/blueprint_tactical/DESIGN.md:
- A design philosophy document.
- Describes the intended UI language as "Architectural Curator".
- Useful for styling decisions, but it is not enforced consistently across the implementation.


2. PRODUCT / DOMAIN MODEL

The product appears to be an administrative dashboard for a facility or ICT centre with these feature areas:
- Internet lounge visitor logging / check-in and check-out records
- Internet QR token creation for temporary access
- Room and event booking / event program scheduling
- Device registry and remote control / monitoring concepts
- Media storage / file management
- Dashboard overview / operational stats

Branding is inconsistent in places:
- "GK IAC Manager"
- "FaciliQ"
- "Ghana-Korea IAC"
- public landing page imagery about Ghana-Korea partnership

Do not assume naming consistency across modules; the product identity is still evolving.

4. HOW THE APP IS BOOTSTRAPPED

Backend entry point:
- backend/server.js

What server.js does:
- loads environment variables
- connects to MongoDB
- configures JSON parsing, cookies, CORS, and IP rate limiting
- mounts public auth routes at /api/auth
- mounts protected routes at /api
- starts the Express server

Important note:
- backend/src/app.js exists but is empty and currently unused.
- The real backend bootstrap is server.js, not src/app.js.
- CORS is currently configured for http://localhost:3000.
- There is an app-wide rate limiter set to 50 requests per 15 minutes.

Frontend entry points:
- frontend/iacmanager/app/layout.tsx
- frontend/iacmanager/app/page.tsx
- frontend/iacmanager/app/login/page.tsx
- frontend/iacmanager/app/dashboard/*

Next middleware:
- frontend/iacmanager/middleware.ts
- protects non-public routes based on a refreshToken cookie

6. BACKEND ARCHITECTURE

6.1 Core backend files

- backend/server.js
  Main server bootstrap, middleware, route mounting, and global error handler.

- backend/src/config/db.js
  MongoDB connection helper.

- backend/src/middleware/auth.js
  JWT access-token protection middleware plus role restriction middleware.

- backend/src/utils/jwt.js
  JWT sign/verify utilities for access tokens, refresh tokens, and "ticket" tokens.

- backend/src/routes/auth.js
  Public auth routes: register, login, refresh, logout.

- backend/src/routes/protected.js
  Protected API root. Mounts feature routers after calling protect middleware globally.

- backend/src/routes/urls/lounge.js
  Internet lounge visitor records.

- backend/src/routes/urls/internet_token.js
  Internet token issuance and retirement.

- backend/src/routes/urls/EventPrograms.js
  Event / booking CRUD.

- backend/src/routes/urls/deviceStatus.js
  Device registry CRUD.

Architectural reality:
- There is no controller/service abstraction in practice.
- Route files directly perform request validation, normalization, database access, and response formatting.
- If you change a feature, the route file is usually the true source of behavior.


6.2 Auth flow on the backend

Auth model:
- Access token is expected in Authorization: Bearer <token>.
- Refresh token is stored as an httpOnly cookie named refreshToken.

Main pieces:
- signAccessToken(userId)
- signRefreshToken(userId)
- signAccessTicket(userId, duration)
- verifyAccessToken(token)
- verifyRefreshToken(token)

protect middleware:
- reads Authorization header
- verifies access token
- fetches user by decoded id
- attaches req.user

restrictTo(...roles):
- checks req.user.role
- compares lower-cased role against the allowed roles

Mounted route behavior:
- /api/auth/* is public
- /api/* in protected.js is behind protect middleware


6.3 Protected route map

Mounted in backend/src/routes/protected.js:

- frontend/iacmanager/context/AuthContext.tsx
  Central auth context.
  Tracks token, user, loading state, and logout/login actions.

- frontend/iacmanager/src/lib/api.ts
  Tiny fetch wrapper for GET/POST/PATCH/DELETE.
  Adds bearer token if provided.
  Sends credentials: include.

- frontend/iacmanager/middleware.ts
  Redirects to /login if refreshToken cookie is missing.
  Redirects to /dashboard/home if refreshToken exists and user visits a public route.

Auth flow intended by the frontend:
- login page calls AuthContext.login()
- login posts to /api/auth/login
- backend returns accessToken and sets refreshToken cookie
- middleware uses cookie to allow dashboard navigation
- AuthContext tries to refresh token on mount by calling /api/auth/refresh

9. FRONTEND DATA FLOW BY FEATURE

9.1 Login flow

Files to read:
- app/login/page.tsx
- context/AuthContext.tsx
- src/lib/api.ts
- backend/src/routes/auth.js

Flow:
1. User enters email and password on login page.
2. Login page calls AuthContext.login(email, password).
3. AuthContext.login posts to /api/auth/login.
4. Backend returns accessToken and user object, and sets refreshToken cookie.
5. Frontend stores access token in React state.
6. Login page pushes to /dashboard/home.
7. Next middleware also allows dashboard access because the refreshToken cookie exists.


9.2 Lounge visitor records

Files to read:
- backend/src/routes/urls/lounge.js
- backend/src/models/InternetLounge.js
- app/dashboard/internetLounge/page.tsx
- app/components/partials/AddModuleLounge.tsx

Flow:
1. Dashboard page fetches /api/users/lounge-data with pagination and optional date/id filters.
2. Modal collects form fields like full_name, contact, user_id, user_id_type, gender, user_time_in, user_time_out.
3. Route normalizes those fields into the InternetLounge schema.
4. Page shows table rows and basic derived metrics like average stay and average checkout time.


9.3 Bookings / event programs

Files to read:
- backend/src/routes/urls/EventPrograms.js
- backend/src/models/booking.js
- app/dashboard/bookings/page.tsx
- app/components/partials/booking_tables.tsx

Flow:
1. Dashboard page fetches /api/bookings/event-program.
2. Booking table renders records and provides edit/delete actions.
3. Add/edit modal returns a form payload.
4. Page sends POST or PATCH depending on whether it is an update.


9.4 Devices

Files to read:
- backend/src/routes/urls/deviceStatus.js
- backend/src/models/devices.js
- app/dashboard/devices/page.tsx
- app/components/partials/Adddevicemodules.tsx

Flow:
1. Devices page fetches /api/devices/devicStatus.
2. User can register a device, edit a device, or soft-delete a device.
3. Modals collect the full device object and send it back via POST/PATCH/DELETE.
4. The page then refetches the registry.


9.5 Internet QR tokens

Files to read:
- backend/src/routes/urls/internet_token.js
- backend/src/models/internettoken.js
- app/dashboard/internetToken/page.tsx
- src/utils/jwt.js

Flow:
1. Page fetches the currently active token from /api/ticketing/sign-ticket.
2. Page can request token creation through /api/ticketing/post-ticket.
3. Backend signs a JWT ticket token and stores it in Mongo.
4. Frontend generates a QR code from the returned token string.

Reality check:
- The page mixes real token fetch/create behavior with mock session/expiry UI.

11. IMPORTANT INCONSISTENCIES AND CAVEATS

This section is the most important thing for another coding model to understand before making changes.

11.1 Business logic is route-centric, not layered
- Ignore the empty controllers/services directories unless you are intentionally introducing a new architecture.
- Most backend changes belong directly in route files today.

11.2 Frontend and backend naming are not fully aligned
- Device endpoints on the backend use /devicStatus and /submit-devicStatus.
- The frontend devices page sometimes calls /api/devices/${id} instead of /api/devices/devicStatus/${id}.
- The frontend lounge page deletes through /api/users/lounge-data/:id, while the backend delete route is /api/users/lounge/:id.
- Sidebar links do not always match real app routes.
  Example:
  - sidebar uses /dashboard/lounge but the real page is /dashboard/internetLounge
  - sidebar uses /dashboard/internet_token but the real page is /dashboard/internetToken

11.3 Auth flow has real structural issues
- frontend/src/lib/api.ts imports useAuth() inside a plain utility function. That is not a safe React hook usage pattern.
- AuthContext expects refreshToken in some places, but backend refresh route only returns a new accessToken.
- The backend refresh route relies on the cookie, while the frontend helper also tries to send an Authorization header for refresh.
- backend/src/routes/auth.js references redis in login logic, but no redis client is imported or initialized there.
- backend/src/routes/auth.js register flow uses error/ errors inconsistently.

11.4 Schema and enum mismatches exist
- Booking/event enums differ between backend schema and frontend types/options.
- Device route checks req.user.department, but User schema has no department field.
- Device schema duplicates security and does not clearly define all fields used by the route.
- Lounge timestamps are strings, but the frontend treats them as dates.

11.5 Feature completeness varies a lot
- If a page looks polished, do not assume it is fully wired.
- Media page is the clearest example: it is a UI prototype with local state, not a persisted feature.
- The token page is only partly wired:
  - createToken uses apiPost() but then treats the return value like a raw fetch Response
  - retireToken uses fetch() directly instead of the shared API helper and does not send auth consistently
- Some legacy components still exist beside newer implementations, so not every similarly named file is still active in the current page flow.

11.6 Case sensitivity may matter on non-Windows deployments
- Some imports use different file casing than the actual filename.
- Example:
  protected.js imports ../models/internetLounge while the file is InternetLounge.js.
- This works on case-insensitive filesystems but may fail on Linux.

11.7 Styling approach is mixed
- Tailwind classes
- CSS modules
- inline style objects
- global CSS variables
- static prototype HTML

There is no single design system implementation layer. The design language is aspirationally documented but inconsistently applied.

11.8 Encoding / text cleanliness
- Some files show mojibake or garbled characters.
- Be careful with text edits and output encoding.
- Prefer plain ASCII unless the file already cleanly uses Unicode.

11.9 No obvious test suite
- There are no visible unit/integration tests in the explored source.
- Changes should be verified carefully by reading the flow end to end.

13. PRACTICAL GUIDANCE FOR CLAUDE

When changing this codebase:
- First identify whether the target feature is real, mock, or hybrid.
- Read both the page component and the matching backend route before making assumptions.
- Expect business rules to live in route files and UI behavior to live in page-level client components.
- Do not "clean up" route names, enum values, or field names casually; many mismatches are already baked into both sides.
- If you fix a backend field or route name, immediately check every corresponding frontend call site.
- Be careful with auth changes because cookies, access tokens, middleware, and React context all participate in the flow.
- For device and booking changes, validate enum spelling on both frontend and backend before editing.
- If you want to introduce a cleaner architecture, treat it as a deliberate refactor rather than assuming one already exists.


14. BOTTOM LINE

This is not a greenfield, fully normalized monorepo. It is a working but uneven product codebase where:
- the backend is the clearest source of truth for live data behavior,
- the Next.js app is the real UI surface,
- design prototypes still coexist beside the main app,
- and a number of integration gaps remain between schema, route, and frontend expectations.

The best way to generate good code here is to be conservative, trace each feature from UI to route to model, and treat inconsistencies as part of the current system rather than accidental noise.
